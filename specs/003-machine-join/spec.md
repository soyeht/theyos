# Feature Specification: Phase 3 - Machine Join Ceremony with Owner Confirmation and Shamir Splitting (theyOS)

**Feature Branch**: `003-machine-join`
**Created**: 2026-05-06
**Status**: Draft
**Input**: User description: "Phase 3 - Add a 2nd theyOS machine to an existing single-machine household via QR or LAN Bonjour, with owner iPhone confirming the join biometrically. Backend half of household-protocol §5 (joining ceremony, MachineCert), §6 (Shamir splitting of HH_priv on first 2nd-machine join), §11 (soyeht://household/pair-machine QR), §12 (POST /api/v1/household/join-request endpoint), §13 (Bonjour pair-machine announcement), and the cross-repo path that delivers a pending join-request to the owner iPhone for biometric confirmation. Stories 2 (LAN) and 3 (remote QR over Tailscale) converge on the same ceremony. Atomic Shamir transition: either both machines confirmed and shards distributed or aborted with rollback to sole-shard. Anti-phishing fingerprint matching on both sides. Out of scope: gossip/CRL (Phase 4), invites/DeviceCert/multi-device (Phase 5), Claw placement."

**Reference contract**: `docs/household-protocol.md` sections 5, 6, 11, 12, 13, 17, and 18; Phase 2 owner-pairing primitives in `specs/002-owner-pairing-auth/spec.md`.

## User Scenarios & Testing *(mandatory)*

The actors are the owner (already paired in Phase 2 with a PersonCert held on their iPhone in the Secure Enclave), the founding theyOS machine M1 (single-machine household with sole-shard root custody), the candidate joining theyOS machine M2 (freshly installed, not yet a member), and the operator running the installer on M2's console. This phase upgrades theyOS from one machine to two: M2 ends up with a household-signed MachineCert, both machines hold a Shamir shard of the household root, and the household root no longer exists in any single device's custody.

### User Story 1 - Owner-confirmed machine join via remote QR (Priority: P1)

The operator runs the theyOS installer on a brand-new candidate machine M2 over Tailscale (different LAN from M1). The installer mints a fresh machine keypair, opens a join window, and prints a `soyeht://household/pair-machine` QR plus a short anti-phishing fingerprint of M2's machine public key. The owner scans the QR with the Soyeht iPhone app over Tailscale. The app surfaces M1's confirmation prompt showing the same fingerprint and the candidate's hostname. The owner verifies the fingerprint against what is printed on M2's console, approves with biometry, and the ceremony completes: theyOS issues a MachineCert for M2, performs the destructive sole-shard → 2-shard Shamir split of the household root, and returns the MachineCert and M2's shard to the joining installer. M2 persists its membership and the household record.

**Why this priority**: This is the only way to grow a household beyond one machine when the owner is not on the candidate's LAN. Without it, the product cannot scale beyond the founding Mac. Story 2 (LAN auto-discovery) is a UX optimization on top of the same ceremony; the join logic and security properties live here.

**Independent Test**: Start from a Phase 2 household (one machine, one paired owner). Run the theyOS installer on a second machine reachable only via Tailscale. Scan the printed QR with the owner-paired test harness, approve. Confirm M2 receives a valid MachineCert chaining to the household root, both machines hold mutually consistent Shamir shards, and the join window is consumed.

**Acceptance Scenarios**:

1. **Given** a single-machine household with an active owner PersonCert and no second machine, **When** the operator runs the installer on M2 with `transport=tailscale`, **Then** M2 prints a `soyeht://household/pair-machine` QR carrying its public key, a one-shot nonce, an expiry, and a Tailscale address, plus a short anti-phishing fingerprint on the console.
2. **Given** the QR has been scanned by the owner-paired iPhone (which decodes every QR field and verifies the candidate's signature over the bound m_pub/nonce/hostname/platform locally), **When** the iPhone forwards the resulting signed join request to theyOS over Tailscale and the owner submits a fresh biometric approval, **Then** theyOS issues a household-signed MachineCert for M2, splits the household root into Shamir shards across {M1, M2}, returns M2's shard with the MachineCert, and consumes the join window.
3. **Given** the ceremony completes, **When** M2 stores the response and the operator restarts theyOS on either machine, **Then** the household record on each machine reflects two members, the MachineCert chain validates against the household root public key, and neither machine alone can reconstruct the household private key in software memory without a Shamir threshold operation.

### User Story 2 - Owner-confirmed machine join via LAN auto-discovery (Priority: P2)

The operator runs the theyOS installer on a candidate machine M2 on the same LAN as M1. M2 advertises itself on the LAN under a Bonjour service that distinguishes the join intent from the Phase 2 device-pairing intent. M1 picks the announcement up automatically, raises a join confirmation request to the already-paired owner iPhone with M2's hostname and fingerprint, the owner approves biometrically, and the ceremony completes without anyone scanning a QR. The fingerprint shown on the owner iPhone matches the fingerprint M2's installer prints on its console.

**Why this priority**: This is the Apple-grade "no manual steps" UX for the common case (new home server arrives on the same Wi-Fi). It reuses the ceremony from Story 1 with a different transport for the join-request announcement; the security envelope is identical. Lower priority than Story 1 because Story 1 covers more deployment topologies.

**Independent Test**: Start from a Phase 2 household on a LAN with mDNS reachable. Run the theyOS installer on a second machine on the same LAN with `transport=lan`. Confirm the founding machine detects the announcement, raises a confirmation prompt to the owner-paired test harness within seconds, the owner approves, and the resulting MachineCert and Shamir shards match the Story 1 outcome bit-for-bit.

**Acceptance Scenarios**:

1. **Given** the founding machine is publishing the household Bonjour service on the LAN, **When** M2's installer advertises itself with the join intent, **Then** the founding machine notices the announcement within seconds and surfaces a join confirmation containing M2's hostname, M2's machine public key, and the same anti-phishing fingerprint M2 has printed locally.
2. **Given** the owner iPhone is reachable from the founding machine, **When** the founding machine surfaces the LAN-discovered join request, **Then** the owner sees a confirmation prompt showing the candidate's hostname and fingerprint and can approve biometrically without scanning anything.
3. **Given** Bonjour discovery is unavailable on the LAN (e.g., mDNS blocked), **When** the operator runs the installer on M2, **Then** the installer falls back to printing the Story 1 QR rather than waiting indefinitely, and the rest of the ceremony proceeds via the Story 1 path.

### User Story 3 - Atomic Shamir transition with rollback on failure (Priority: P1)

The household root, which lives entirely in the founding machine's custody while the household has one machine, must transition to a 2-shard Shamir-split secret the first time a second machine joins. This transition is destructive (the original sole-shard custody ceases to exist) and must be atomic across both machines: either both end up with valid mutually consistent shards and a household-signed MachineCert for the new machine, or the founding machine remains in sole-shard mode and no MachineCert is issued. Partial states (one machine holding a shard while the other does not) are forbidden.

**Why this priority**: This is the only operation in the lifetime of the household where the root key custody changes shape. A partial failure here produces an unrecoverable household, which violates the no-SPOF principle. It must be tested and observable independently of the join transport.

**Independent Test**: Inject failures at each stage of the Story 1 ceremony — owner approval timing out, network partition between owner iPhone and theyOS during confirmation, candidate machine becoming unreachable mid-ceremony, candidate machine failing to persist its returned shard. After each injected failure, the founding machine MUST remain in single-machine sole-shard mode with no MachineCert issued for the candidate, and a fresh ceremony with the same or a different candidate MUST succeed afterwards.

**Acceptance Scenarios**:

1. **Given** a join ceremony is in progress, **When** the owner declines confirmation or the confirmation window expires, **Then** the founding machine destroys any in-memory ephemeral material related to the ceremony, retains its existing sole-shard custody intact, and the candidate receives a generic unauthenticated outcome from the join endpoint.
2. **Given** the owner has approved confirmation, **When** the candidate becomes unreachable before persisting its returned shard, **Then** the founding machine MUST NOT commit the new household record (membership = 2) or destroy its sole-shard custody; the household state visible to the founding machine after the ceremony aborts MUST be byte-equivalent to the state before the ceremony began.
3. **Given** both machines have committed the new household record and shards, **When** either machine restarts, **Then** the household record on disk shows two members and Shamir parameters appropriate for two machines, and any operation requiring household-signed authority needs a Shamir threshold reconstruction (not sole-shard custody) on both machines.

### Edge Cases

- **No active owner**: A household with no owner PersonCert (Phase 2 not yet completed) MUST refuse all join-request traffic; the join endpoint returns a generic unauthenticated outcome and emits no QR.
- **Already two-machine household**: A household whose membership is already at the maximum supported by the v0.1 protocol simply rejects further join attempts with a generic outcome until invites/multi-device support is delivered in later phases.
- **Replayed join-request**: A second `join-request` carrying the same candidate machine public key and the same nonce as a request that already produced a MachineCert MUST NOT issue a second MachineCert; the same response MAY be returned within the original join window's TTL, after which the request is rejected.
- **Concurrent join attempts from two different candidates**: At most one ceremony is active per household at any moment. A second candidate's request received while a ceremony is in flight is rejected with a generic outcome and may be retried after the active ceremony settles.
- **Owner iPhone unreachable at confirmation time**: The ceremony fails closed within a bounded confirmation window; the founding machine surfaces a retryable failure on the candidate's installer console without revealing why (network vs. user denial vs. unknown owner).
- **Tampered local household state**: If the founding machine's stored sole-shard or household record fails self-validation at ceremony start, the ceremony refuses to start; no MachineCert is issued and the operator is told to recover from backup or re-bootstrap.
- **Permanent post-approval candidate loss**: If the owner has approved and the founding machine has issued a `MachineCert` and posted the JoinResponse to the candidate, but the candidate becomes permanently unreachable before the founding machine can confirm the candidate's persistence (per `FR-013a`), the founding machine rolls back to single-machine sole-shard custody after a bounded recovery window. The candidate's possibly-persisted MachineCert is treated as orphan and is not honored by the household; if the candidate later returns it must re-do the ceremony from scratch.
- **Fingerprint mismatch suspected by owner**: If the owner iPhone shows a fingerprint that does not match what the candidate's installer prints, the owner declines and the ceremony aborts atomically (per Story 3); no diagnostic difference is exposed between "owner declined" and "owner timed out".
- **Bonjour announcement received from a candidate that is not actually trying to join**: The founding machine MUST require the candidate to also POST a join-request carrying the matching nonce; a mDNS announcement alone never produces a confirmation prompt.
- **QR scanned twice by the same iPhone, or by two devices**: Single-use is enforced server-side via the nonce; the first scan that completes confirmation wins; subsequent scans see the join window closed.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: theyOS MUST accept a candidate machine join only while the household has exactly one current member, an owner PersonCert exists, and no other join ceremony is in progress.
- **FR-002**: The candidate machine's installer MUST mint a fresh EC P-256 machine keypair locally before initiating the join and use the corresponding public key as the candidate identifier in all join messages. The default platform-appropriate identity-key residency rules apply (Secure Enclave on macOS, kernel keyring or Secret Service on Linux, software-fallback file-based keystore at mode `0o600` elsewhere), **with one Phase 3 carve-out**: this feature's Shamir-split transition (FR-021) requires the raw 32-byte M_priv scalar for ECDH-based shard decryption, which Apple's Secure Enclave by design will not release. On macOS, the candidate machine MUST therefore run with `THEYOS_FORCE_SOFTWARE_KEYS=1` set during bootstrap so that `M_priv` lives under the software-fallback keystore for Phase 3 to complete. The same flag MUST remain set across subsequent daemon boots on macOS, because the default policy on a re-bootstrap would otherwise attempt to materialise `M_priv` against the Secure Enclave path and fail closed when Phase-3 shard decryption needs the scalar. A future phase MAY introduce a threshold-signature primitive that operates on the SE handle without exporting bytes; until that lands, FR-002 and FR-021 must be read together on macOS.
- **FR-003**: The candidate machine's installer MUST advertise itself on the local network using the household's Bonjour service in a way that distinguishes the machine-join intent from the existing Phase 2 device-pairing intent, so the founding machine never confuses a candidate machine with a candidate device.
- **FR-004**: The candidate machine's installer MUST render a `soyeht://household/pair-machine` URI as a QR carrying protocol version, candidate machine public key, one-shot nonce, hostname, platform, transport hint, address (for Tailscale or LAN), an absolute expiry timestamp, **and a self-signed challenge signature that cryptographically binds the m_pub, nonce, hostname, and platform fields together** so neither the QR nor any UI value displayed to the owner can be tampered without invalidating the signature. The QR is therefore a self-contained signed credential the owner iPhone forwards to the founding machine in a single network hop, without contacting the candidate.
- **FR-005**: theyOS on the founding machine MUST expose a join-request endpoint that accepts a candidate's join-request payload over the household network (Tailscale by default, LAN where applicable) and stages a pending owner-confirmation event for the owner iPhone to retrieve.
- **FR-005a**: theyOS MUST expose an authenticated owner-events endpoint that the owner iPhone polls over Tailscale to retrieve pending events (including a pending join-request). The endpoint MUST hold the request open until a new event becomes available or a server-side timeout elapses, return events in monotonic-cursor order so the iPhone can resume from its last seen cursor across reconnects, and authenticate every poll via the owner PersonCert's proof of possession.
- **FR-005b**: When the owner iPhone is not currently holding an open poll and a new owner-targeted event is staged, theyOS MUST send an opaque silent push notification to the owner device through Apple's push delivery service. The push payload MUST carry no event data, no candidate identifier, no fingerprint, and no household identifier beyond what is required by the platform to deliver the push at all; its sole purpose is to wake the iPhone so it can open Tailscale and resume the long poll.
- **FR-005c**: All authoritative event content (candidate machine public key, candidate hostname, candidate platform, fingerprint, expiry, any owner-actionable payload) MUST flow exclusively over the authenticated owner-events long poll over Tailscale; theyOS MUST NOT place such content in any push payload, anywhere, at any time.
- **FR-005d**: theyOS MUST expose an authenticated owner-device push-token registry endpoint that the owner iPhone uses to register and rotate the platform-issued push token associated with its current installation. Updates MUST require fresh proof of possession of the owner person private key.
- **FR-005e**: The push token registered by the owner iPhone MUST be persisted on the founding machine, and MUST be propagated to the second machine as part of the join ceremony in this phase (so the new member starts with the same household-private artifact every other member already holds). The founding machine remains the sole dispatcher in this phase; later phases extend dispatch to other members via gossip replication.
- **FR-006**: theyOS MUST present, to the owner device confirming a join, the candidate's hostname, platform, machine public key, and a short human-comparable anti-phishing fingerprint derived deterministically from the candidate machine public key.
- **FR-007**: The anti-phishing fingerprint format MUST be byte-for-byte identical between the candidate's installer console output and the owner device's confirmation UI so the owner can compare them directly. The format is **six words from the standard BIP-39 English word list**, derived deterministically from the candidate machine public key by hashing the 33-byte SEC1 representation with BLAKE3-256, taking the first 66 bits, and mapping each successive 11-bit chunk to one BIP-39 word. The fingerprint string MUST be rendered as exactly six lower-case words separated by single ASCII spaces on both sides; no other punctuation, no per-side stylization, no truncation.
- **FR-008**: theyOS MUST require a fresh proof of possession of the owner's person private key, gated by biometry on the owner device, before treating a confirmation as authoritative; bearer-style approvals are forbidden.
- **FR-009**: theyOS MUST verify, before issuing a MachineCert, that the candidate has demonstrated possession of the machine private key corresponding to the public key in the join-request, so a leaked QR alone cannot be used by an attacker who does not also control the candidate machine's private key.
- **FR-010**: On owner approval, theyOS MUST issue exactly one MachineCert for the candidate machine, signed by the household root, carrying the candidate's machine identifier, public key, hostname, platform, and join time, and chain the MachineCert deterministically to the household root public key.
- **FR-011**: On owner approval, theyOS MUST destructively transition household root custody from sole-shard mode to a Shamir-split secret distributed across the founding machine and the new machine; the original sole-shard custody MUST NOT continue to exist after the transition completes.
- **FR-012**: When the household first reaches two machines, theyOS MUST split the household root scalar with Shamir parameters `(k=2, n=2)` — exactly two shards, both required for any future household-root operation. Each member machine holds exactly one shard; no other custodian holds a shard in this phase. The chosen `(k, n)` MUST be recorded in the persisted household record on both machines and in the response returned to the candidate.
- **FR-012a**: theyOS MUST surface to the operator on the candidate's installer console, immediately after a successful join, that the household is currently at the protocol's minimum redundancy (any single permanent machine loss equals household loss) and that adding a third machine is the supported way to gain loss tolerance. The wording is informational and does not gate ceremony completion.
- **FR-012b**: This phase MUST NOT introduce additional shard custodians (such as the owner iPhone holding a shard, or an exported recovery code). Re-sharding to a higher-availability `(k, n)` when the household later admits a third machine, or any other future custodian model, is explicitly out of scope of this phase and is deferred to a later phase that will perform proactive secret sharing per the household protocol §6.
- **FR-013**: The Shamir transition and MachineCert issuance MUST be atomic from the perspective of both machines: either the new household record (membership = 2, new Shamir parameters) is committed on the founding machine **and** the candidate has persisted its MachineCert and shard, or neither side persists changes and the founding machine remains in single-machine sole-shard mode.
- **FR-013a**: After the owner has approved, if the founding machine cannot confirm that the candidate has persisted its MachineCert and shard within a bounded recovery window, the founding machine MUST roll back to single-machine sole-shard custody. Any MachineCert the candidate may have persisted before becoming permanently unreachable in that window MUST be treated as orphan: if the candidate later returns it MUST re-do the join ceremony from scratch and obtain a fresh MachineCert. The household never trusts a MachineCert whose corresponding member is not also reflected in the household record on the founding machine.
- **FR-014**: After successful join, theyOS MUST return to the candidate the issued MachineCert, the candidate's Shamir shard, the household record reflecting two members, and a peer list sufficient for future household-scoped traffic between the two machines.
- **FR-015**: theyOS MUST treat repeated join-request submissions carrying the same candidate machine public key and the same nonce within the join window's TTL as the same logical request: the second submission MUST NOT cause issuance of a second MachineCert, MUST NOT cause a second Shamir transition, and SHOULD return the same MachineCert, shard, and peer list as the first successful response when the original ceremony completed successfully.
- **FR-016**: Once a join window is consumed (by completion, expiry, or operator cancel), any further join-request bound to the same nonce MUST be rejected with a generic unauthenticated outcome that does not reveal whether a join window ever existed.
- **FR-017**: theyOS MUST refuse to start a join ceremony when the local household state, owner PersonCert, or sole-shard custody fails self-validation against the household root, and MUST surface the refusal as a generic unavailability outcome to the candidate without leaking which validation step failed.
- **FR-018**: theyOS MUST NOT accept a candidate's join-request payload as a substitute for owner confirmation; owner approval is the only condition under which a MachineCert is issued.
- **FR-019**: theyOS MUST log security-relevant events (join window opened, join-request received, owner prompt forwarded, owner approved, owner declined, owner timed out, ceremony aborted, ceremony committed, Shamir transition committed) without recording private keys, raw signatures, full nonces, or full Shamir shards.
- **FR-019a**: Every error response from a household-scoped endpoint introduced or modified by this phase (including the join-request endpoint, the owner-events long-poll, owner approve/decline, and the push-token registry) MUST use deterministic CBOR for the response body, identical to the wire format of the corresponding success bodies. No mixing of CBOR success bodies with JSON error bodies. Generic pre-commit failures carry the deterministic CBOR `{"v": 1, "error": "unauthenticated"}` (HTTP 401). Post-commit partial-failure outcomes — i.e., owner-approve failures that surface AFTER M2 has returned `FinalizeAck` and committed its side of the ceremony — carry the deterministic CBOR `{"v": 1, "error": "internal"}` (HTTP 500), so the iPhone client can distinguish "ceremony refused" from "ceremony in an indeterminate state, do not auto-retry". See `contracts/owner-events.md` "Response" subsection for the exhaustive list of 500-eligible failure modes.
- **FR-020**: This feature MUST remain limited to admitting a second machine to an existing single-machine household. It MUST NOT add gossip replication, CRL replication, person invitations, DeviceCert delegation, multi-device-per-person flows, third-machine joining, or Claw placement and migration; those remain assigned to later phases.
- **FR-021**: This feature's Shamir-split transition MUST operate on the raw 32-byte EC scalar of `HH_priv` and on the candidate's raw 32-byte M_priv scalar (for ECDH-based shard encryption / decryption). Apple's Secure Enclave by design refuses to export private scalar bytes, so on macOS the founding machine's `HH_priv` and the candidate's `M_priv` MUST live under the software-fallback keystore (file-based, mode `0o600`) for Phase 3 to complete. Operators run with `THEYOS_FORCE_SOFTWARE_KEYS=1` set during bootstrap on macOS to enforce this. A future phase MAY introduce a threshold-signature primitive that operates on the SE handle without exporting bytes; that is explicitly out of scope here. The wire response on the SE-incompatible path remains the generic `401 unauthenticated` (FR-019a / R14); the actionable diagnosis surfaces only via local tracing on the affected machine.

### Key Entities *(include if feature involves data)*

- **Candidate Machine**: A theyOS installation that is not yet a household member and is requesting to join. Identified by its EC P-256 machine public key. Holds its own machine private key in platform-appropriate residency.
- **Join Window**: A short-lived state on the founding machine that authorizes exactly one machine-join confirmation. Carries the candidate's machine public key, the one-shot nonce, the transport/address hint, the expiry timestamp, and the fingerprint string presented to the owner.
- **Join Request**: The wire payload carrying the candidate's identity, proof of possession of its machine private key, and the QR or LAN-discovery-derived nonce.
- **Owner Confirmation Prompt**: The cross-repo carrier from theyOS to the owner iPhone that surfaces a pending join, requests biometric proof of the owner's person private key, and returns the owner's signed approval (or implicit decline by timeout). Delivered via authenticated long poll over Tailscale, with an opaque silent push used only to wake the iPhone when it is not currently polling.
- **Owner Events Cursor**: A monotonic, persistent value identifying the owner iPhone's resume point in the household's stream of owner-targeted events, used so disconnects do not lose events and reconnects do not replay events the owner has already seen.
- **Owner Device Push Token**: The platform-issued push token associated with the owner iPhone's current installation, registered by the iPhone over an authenticated channel and persisted by the household for use by any member machine to dispatch an opaque push tickle.
- **Anti-Phishing Fingerprint**: A short, deterministic, human-comparable representation of the candidate's machine public key, rendered identically on the candidate's console and the owner's confirmation UI.
- **MachineCert**: The household-signed capability certificate attesting that the candidate machine is a member of the household, chaining to the household root public key.
- **Shamir Shard**: One of the parts into which the household root private key is split when the household admits its second machine. Each member machine holds one shard, encrypted under that machine's own key material.
- **Household Record (post-join)**: The local persisted record that, after a successful ceremony, lists two members, the new Shamir parameters, and the household root public key.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An owner-approved Story 1 (remote, Tailscale) ceremony completes end-to-end (from QR scan to candidate persisting its MachineCert) within 30 seconds under nominal network conditions.
- **SC-002**: An owner-approved Story 2 (LAN, Bonjour) ceremony completes end-to-end within 15 seconds and never requires the operator to scan a QR or type a host argument when LAN discovery is functional.
- **SC-003**: In 100 Story 3 (failure-injection) trials covering owner decline, owner timeout, candidate disconnect after approval, candidate persistence failure, and founding-machine crash mid-ceremony, the founding machine ends every trial either fully committed (membership = 2 and Shamir-split) or fully rolled back (membership = 1 and sole-shard) — never in a partial state.
- **SC-004**: After a successful join, neither the founding machine nor the new machine alone holds the household private key in any usable plaintext form; reconstructing it for any future privileged operation requires the Shamir threshold of shards from at least the configured number of machines.
- **SC-005**: In 100 attempts to replay a single completed join-request (same candidate machine public key, same nonce) within the join window TTL, exactly one MachineCert is issued, exactly one Shamir transition occurs, and replays return the same response or a generic unauthenticated outcome — never a duplicate enrollment.
- **SC-006**: 100% of join-requests submitted without a paired owner, with a tampered candidate proof of possession, with a missing or expired nonce, or with a candidate already a member, are rejected with a generic unauthenticated outcome that cannot be distinguished by an external observer.
- **SC-007**: 100% of fingerprint-mismatch scenarios (the candidate's printed fingerprint differs from what the owner sees) end in owner decline and ceremony rollback to single-machine sole-shard mode, with no MachineCert issued.

## Assumptions

- Phase 2 is complete: the founding theyOS machine has bootstrapped a household root, holds it in sole-shard custody appropriate for the platform, and has issued exactly one owner PersonCert. The owner iPhone holds the corresponding owner person private key in its Secure Enclave and is reachable from theyOS over the household network.
- The household network is Tailscale for remote (Story 1) and the LAN for Story 2 (Bonjour). No other network transports are introduced in this phase.
- The candidate machine has a working theyOS installer that can mint its own machine keypair, render a QR, and POST to the founding machine's join-request endpoint. Installer details (CLI shape, terminal rendering) are out of scope of this spec beyond the data they emit and consume.
- The Shamir transition is performed only on the first time a household goes from one machine to two; subsequent membership changes (third machine, removed machine) are out of scope of this phase and addressed by later phases.
- The Shamir transition treats the original sole-shard custody as destructively replaced, consistent with the household protocol's documented edge case for the founding-Mac sole-shard handover.
- Reentrancy of the join-request endpoint is by candidate machine public key plus nonce, not by IP address or hostname; a candidate retried under the same nonce within the join window TTL behaves idempotently.
- An owner confirmation prompt that times out without an explicit approve or decline is treated as decline for the purpose of ceremony rollback; this is intentional, even though the owner did not actively reject, to keep the failure-closed property simple.
- Bonjour service-type and TXT records continue to use the household service introduced in Phase 2; this phase adds machine-join-specific subtype or TXT fields rather than introducing a parallel service.
- The TTL of the join window is the same order of magnitude as the existing Phase 2 pair-device window (a few minutes), unless the cross-repo agreement on confirmation transport requires otherwise.
- No new cryptographic primitives are introduced. All keys are EC P-256, all signatures are 64-byte raw `r || s`, all hashes are BLAKE3-256, all serialization is deterministic CBOR, all secret splitting is Shamir GF(256) over the 32-byte P-256 private scalar, per Constitution v2.0.0 and the household protocol §3.
- The "candidate machine has demonstrated possession of its machine private key" requirement is satisfied by an EC P-256 ECDSA signature produced by the candidate over a deterministic CBOR challenge bound to the join-request payload; the exact challenge shape is a plan-time decision.
- Generic unauthenticated outcomes returned by the join-request endpoint are uniform regardless of the underlying reason (no active window, wrong nonce, owner declined, owner timed out, replay, tampered proof) so an external observer cannot distinguish them.
- The owner-confirmation transport is closed (decided 2026-05-06): authenticated long poll over Tailscale carries all event content, with an opaque silent APNS push used solely to wake the iPhone when no poll is open. APNS payload is by contract empty/opaque so no household metadata reaches the push provider. Cross-repo agreement with the iSoyehtTerm app on the on-the-wire shapes (cursor encoding, event payload, poll timeout, error shapes) is required at plan time.
- The anti-phishing fingerprint format is closed (decided 2026-05-06): six BIP-39 English words derived from the first 66 bits of `BLAKE3-256(M_pub_SEC1)`, lower-case, single-space-separated, identical on both sides. The iSoyehtTerm app must use the same derivation; cross-repo agreement on this is locked.
- The Shamir parameters at the first two-machine state are closed (decided 2026-05-06): `(k=2, n=2)`, no extra custodian, with explicit operator-facing acknowledgement that any single permanent machine loss equals household loss until a third machine is added. Higher-availability re-sharding is a known follow-up scoped to a later phase.
- All open architectural items called out at briefing time are now closed. Other plan-time decisions (Shamir-transition commit ordering specifics, idempotent replay response shape, exact event payload schema, polling timeouts, cursor encoding) are deliberately deferred to the planning phase and tracked there.
